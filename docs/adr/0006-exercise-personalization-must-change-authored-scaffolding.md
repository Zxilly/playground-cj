# Exercise Personalization Must Change Authored Scaffolding

Exercise difficulty is a versioned deterministic transformation of an immutable Exercise Template, not a descriptive label chosen by the model. Policy v2 has exactly three effective variants for validated code-output templates: Standard keeps authored starter code and withholds hints, Easy keeps starter code and exposes the template's authored hints, and Hard withholds both starter code and hints. Expected answers, source requirements, and evaluator behavior never change.

Easy creation fails when the selected template has no authored hint, and Hard creation fails when there is no substantive authored starter code to remove. This rejects no-op paths where Easy or Hard could persist a task identical to Standard under a different label. Failure-based personalization accepts only the aggregate-derived bounded failure suffix after the most recent success for the same Concept, Learning Skill, and Learning Contract. The teacher copies these exact candidates from the Content Pack read; it cannot revive an older resolved failure or infer a candidate from a truncated recent-activity window. Applicable failure or Remediation references select Easy, are subject to the same authored-hint requirement, and cannot be combined with a contradictory Hard target. Placement Checks remain standardized and reject all personalization.

Every Exercise Instance persists its effective difficulty, exact generated task, bounded inputs, and policy version so aggregate integrity can re-derive it. Because policy v2 changes the meaning of already persisted instances, Classroom Snapshot and IndexedDB storage advanced from v5 to v6 with no implicit migration.

The aggregate later replaced the ambiguous `recentErrorPatternIds` field with `unresolvedFailureEvidenceIds` and made both command validation and historical integrity re-derive the success-bounded failure suffix. It also replaced the ambiguous Clarification `readOnly` field with `retainedAsReadOnly`: this is immutable creation-time provenance, not a cached copy of mutable external review availability. Reopening retained history after the same exact Content Version moves pending → approved, approved → pending, or approved → revoked must neither rewrite that provenance nor reject the snapshot. Together with canonical retention-suppression identities and removal of unreachable persisted variants, this advances Classroom Snapshot and IndexedDB storage from v6 to v7. Runtime intentionally opens a new v7 database and does not look up, reinterpret, or migrate v6 state.
